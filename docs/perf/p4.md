# Perf report — P4 (voice capture + STT)

Measured 2026-11-22 on the dev laptop (Windows 11 26200, Realtek SoundWire mic), release build.

| Metric | Measured | Budget | Result |
|---|---|---|---|
| binary size | 1.96 MB (2 058 752 bytes) | ≤ 8 MB | pass |
| utterance end → first text token | p50 0.89 s (0.71 / 0.76 / 0.89 / 1.26 / 4.75 s) | ≤ 1.0 s p50 | pass |
| transcription (Voxtral, 0.9–3.8 s clips) | 0.31–0.50 s, one outlier 4.46 s | — | — |
| prewarm on wake (`GET /v1/models`) | 251–582 ms, off the critical path | 2 s timeout | pass |
| VAD start / end vs placed speech | starts +0–48 ms, ends +10–96 ms | ±100 ms | pass |
| STT word error rate (5 fixtures) | 0 / 39 words | ≤ 15 % | pass |
| capture loop allocations | 0 in 1 s (16 289 samples) | 0 | pass |
| mic open → first packet | 105–310 ms | 350 ms (was 80 ms) | pass after budget change |

## Notes

**Binary +145 KB over P3** (1 913 344 → 2 058 752 bytes): earshot's network weights are about 95 KB; the rest is
the segmenter, the WAV encoder, WASAPI capture and the voice turn.

**End to end** was measured with `--features dev-inject`: each fixture was played in real time in place of the mic
after 0.5 s of silence, and a second launch triggered the voice wake. The interval runs from the segmenter deciding the
utterance is over (700 ms after the last voiced frame) to the first reply token. That covers the WAV encode, the upload and
transcription, and the first token from `mistral-small-latest`. One run in five had a 4.46 s transcription of a 0.9 s clip, which looks
like service-side variance. The STT timeout is 10 s.

**VAD.** earshot replaces WebRTC VAD (SPEC CHANGE §2.2). Its score climbs slowly through breathy onsets such as
/s/ and /h/, so the start walks back over frames that score ≥ 0.35 or are at least twice the noise floor. Without that,
"How far…" started 112 ms late. Ends run late by the detector's hangover; the worst case is +96 ms on "Open the browser.".

**Not re-measured:** idle RAM. Nothing new is allocated before the first voice wake. The capture thread, ring
(64 KB), detector (~8 KB) and segmenter exist only while listening.

## Decided: mic open latency

The spec wants the first mic packet within 80 ms of wake. On this machine `IAudioClient::Initialize` alone takes
70–260 ms while the SoundWire endpoint powers up. Neither the format nor the flags change that. With the endpoint already running,
the first packet arrives in 18–24 ms. On an initialized client, Start → first packet takes 37 ms (5 ms on a restart).

Anything said before the first packet is lost. In the first hand test every utterance that was found began at least 1.0 s
into the audio, so nothing suggests it happens in practice, but this was not tested on purpose. Options:

1. **Keep opening at wake (current).** No mic use while idle. Accept 105–310 ms on this hardware and relax the budget
   to "first packet ≤ 350 ms", noting that it depends on the device.
2. **Initialize at startup, Start at wake.** About 37 ms to the first packet. The audio client stays initialized while idle. It is not yet
   verified whether Windows shows the mic privacy indicator for an initialized but stopped stream. If it does, that
   breaks "indicator only while Listening".
3. **Initialize on head reveal (corner dwell), Start on the hotkey.** A middle path that helps only the corner-wake route.

**Decision (2026-11-22): option 1.** The mic keeps opening at wake and the budget is now 350 ms (SPEC CHANGE in §8).
