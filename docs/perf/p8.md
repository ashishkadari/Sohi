## Notes

**The 8 h parked soak was skipped at the owner's request.** In the 6 minutes it ran, private bytes went from 7.13 to
7.06 MB. That says nothing about hours.

**Memory over the 60 turns.** Private bytes: 5.9 MB after 10 turns, 5.8 after 20, 6.2 after 40, 7.2 after 60, and 7.1
parked. The test instance shares its corner with the Sohi in daily use, and its head was clicked twice: the second
time, shortly before turn 40, the pill took the keyboard and Windows loaded its text input (TextInputFramework, MSCTF,
CoreMessaging, CoreUIComponents, Ninput; GDI objects 13 → 22, USER objects 14 → 28). That explains the working set, 26.7 →
31.8 MB. Whether it also explains the last 1 MB of private bytes is not known: a slow leak per turn is not ruled out. A
second run without clicks would tell.

**Working set after typing.** For the reason above it is about 32 MB once the pill has had the keyboard. The budget is
defined after voice turns only. About 1.6 MB of the 26 is UI Automation, for the pill's text boxes. Third-party
network software on this PC adds some.

**The failed turn.** Transcription failed 14 ms after it began, most likely on a pooled connection the server had just
closed. Such a request is now sent once more (unit-tested; not in the build that was soaked). Another turn was cancelled
by the first click.

**Size.** The C runtime is linked in now, since a clean Windows 11 has no `VCRUNTIME140.dll`. Cold code is built for size:
−0.4 MB of working set and of binary. Rendering and audio stay at `opt-level = 3`.

**Idle CPU.** The budget holds for a pointer far from the corner, and the PC was in use during these runs. The three runs
over budget had no record of the pointer, and being near the corner does not explain them (31 ms at most); what
does is not known.

**First start.** Windows reads a new exe before it runs (178 ms). Later starts take 24 to 28 ms.

**What did not help:** `CoFreeUnusedLibrariesEx` after audio (Windows keeps the audio DLLs loaded).
