## Notes

**Head frame p95 is 0.75 ms; the budget is now ≤ 1.0 ms** (SPEC CHANGE §6, approved 2026-11-22). The old 0.5 ms budget
was never met by frames that reach the screen:

- P1 left `pptDst`/`psize` out of `UpdateLayeredWindowIndirect` when they had not changed. The docs allow that, but
  on this machine the compositor then kept showing the first frame. Because a reveal starts fully transparent, the head
  never appeared at all. v0.1.0 has the same bug, so the P1 figure of 0.44 ms was measured on frames that did not
  reach the screen.
- `fix(win): pass position and size on every layered update` passes both on every frame. Passing the size is what
  matters: position alone still shows nothing. Dirty-rectangle updates still work.
- With the fix, short runs gave 0.69–1.08 ms. Rendering and the swizzle take about 50 µs; the rest is the compositor
  call.

**Idle CPU** is 31–47 ms per 60 s across two 60 s runs, up from 0 ms in P1. That is the 4 Hz corner poll.
`GetProcessTimes` counts in 15.6 ms scheduler ticks, so these are two or three ticks. It is within the 60 ms budget,
but the margin is thin. Lengthening the far poll period, or arming it only near the screen edge, would widen it.

## P2 acceptance (spec §8)

| Criterion | Result |
|---|---|
| A corner dwell of 350 ms wakes; passing through in under 300 ms does not (20 trials, 0 false wakes) | A unit test covers every entry phase × stays of 50/150/299 ms at the 50 ms poll rate, with 0 wakes. Live with `SetCursorPos`: a 200 ms pass did not wake and a 600 ms dwell did. The 20 manual trials have not been run. |
| Dragging with a button held never wakes | A button press resets presence (unit-tested). Not tried live, to avoid clicking in the user's top-right corner. |
| A full-screen D3D app or presentation suppresses corner wake; the hotkey still works | Live: with a borderless full-screen window, `SHQueryUserNotificationState` returned `QUNS_BUSY` and the dwell logged `corner wake suppressed: full-screen app`. After it closed, the same dwell woke. Hotkeys bypass suppression by design. A real D3D game has not been tested. |
| No re-wake within 1.5 s of a retract | Live: a dwell started right after a retract waited, then woke 1.54 s after park. Unit-tested in `visibility` and `wake`. |
| Locking stops polling (log + CPU time) | Lock, unlock, suspend and resume messages posted to the app window: the poll period goes to `None` and back to 250 ms. A real Win+L lock has not been tested. |
| State machine tests cover every Visibility transition, including events mid-animation | A table test covers every (phase, input) pair, plus tests for reversal mid-slide, hover pause and resume, rule changes, and cooldown. Live: a retract during a reveal reversed from 84 % shown. |
| A second launch exits within 50 ms and the first instance logs `wake requested` | 13–22 ms over 5 launches; `wake requested` was logged each time. |
